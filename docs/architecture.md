## Context
- **Product:** DevFest Tacna 2026 "DevFest Space Arcade · Odisea de Código" (roadmap working name: G-App / Interfaz de Mando). Event companion PWA with galactic-exploration gamification: QR scanning, ranks, XP, G-Credits, leaderboard. Key metric: QR check-ins per cadet.
- **Actors:** Cadet (attendee, Google account, picks alias), Staff (scans catering QR), Admin/Organizer (issues ephemeral QRs, manages team, checkpoints, squads, and from phase 3 missions, quadrants, the venue map and narrative, with AI suggestions; controls the stage leaderboard in phase 6). All authenticated.
- **Surfaces:** mobile-first cadet app (dashboard, scanner, pass, missions and map tabs), staff checkpoint view, admin "Centro de Control", stage leaderboard HUD (phase 6).
- **Current phase:** 3 Active Missions & Galactic Quadrants (phase 1 closed 2026-10-09; phase 2 closed in code 2026-10-09). Modules in order: see "Phase 3 build order".
- **Language rule:** UI copy in Spanish; code, identifiers, comments and tests in English.
- **Prepare-early constraints:** user document with alias, role (attendee|staff|admin), squad, xp, credits; XP/credits/QR validation only from the server, never client-trusted; idempotent per cadet+checkpoint records; leaderboard through aggregated/cached reads for mass load.

## Style and layers
**Feature-first with Clean Architecture inside each feature.**
- Each roadmap module is a feature under `src/features/<name>` with `domain/`, `data/`, `ui/` and a public `index.ts`.
- **Dependency rule inside a feature:** `ui → domain ← data`. `domain` imports nothing from React, Next.js, Firebase or other features' internals.
- **Boundary rules:**
  - A feature imports another feature only through its public entries: `index.ts` (client-safe), `server.ts` (server-only, guarded by `server-only`) and, when needed, a light `constants.ts` for code such as `proxy.ts` that must not load SDKs.
  - `shared/` holds no business rules and never imports from `features/`.
  - Cross-feature orchestration (for example "register, then assign squad") lives in `src/app-shell/` as a server action composing public use cases.
  - Circular dependencies are not allowed; if two features need each other's internals, merge them or extract the common part into `shared/`.
- A new roadmap phase adds features. Changing an existing feature requires a Decisions log entry.
- **Why:** modules map 1:1 to roadmap phases and rarely share entities; the economy and rank rules must live in the domain, not in components; the provider (Firebase) is decided, so the full layered ceremony is not needed.

## Framework and provider conventions

**Profiles used:** `frameworks/nextjs.md` (App Router) and `providers/firebase.md`.

**Rendering**
- Server components by default; `"use client"` only for interactivity, browser APIs and subscriptions.
- Cadet routes are dynamic (per-user, cookie-based). No ISR in phase 1. After registration, `revalidatePath("/dashboard")`.
- `app/` stays thin: pages call hooks or server-side use cases wired in `src/app-shell/composition`.

**Auth flow**
1. Client signs in with Google through `FirebaseAuthAdapter` (client SDK, client-only code).
2. Client sends the ID token to `POST /api/auth/session`; the server verifies it with the Admin SDK and issues an HTTP-only session cookie.
3. `src/proxy.ts` (Next.js 16 renamed Middleware to Proxy; Node.js runtime) only checks that the `__session` cookie exists and redirects protected prefixes to `/login`. It never bounces signed-in users away from `/login`, to avoid redirect loops with stale cookies; the login page verifies the session itself.
4. `requireSession()` / `requireRole()` in `src/app-shell/guards.ts` (the DAL) verify the session cookie with the Admin SDK (memoized per render with React `cache`) and read the role from custom claims. Layouts do not re-render on navigation, so checks also run in pages and server actions next to the data. A role mismatch behaves as `notFound()`.
5. Role guard per route group: `(attendee)` requires an attendee, `(staff)` staff or admin, `(admin)` admin.
6. Custom claims (`role`) are set only from server code. A new claim does not appear in the existing cookie, so after registering the client calls `refreshSession()`: it asks Firebase for a fresh ID token and `PUT /api/auth/session` swaps the cookie. The server requires both proofs (valid current cookie and a fresh token of the same user) and skips the 5-minute recent sign-in rule that applies only to new sign-ins. Staff and admin are granted with `scripts/set-role.ts`; cadets get `attendee` at registration. After a claim changes, a fresh session cookie is issued.

**Data access (phase 1)**
- All reads and writes of `users` and `aliases` happen on the server through the Admin SDK, in files marked `import "server-only"`.
- The client Firestore SDK is not used in phase 1; it arrives with realtime in phase 2.
- Repositories return domain entities through mappers; Firestore timestamps are converted at the boundary. Domain never imports Firebase types.

**Data model.** One database serves several editions of the event: everything of an edition lives under `events/{eventId}`, and `config/app.activeEventId` says which edition the app serves (default `devfest-2026`, from `shared/config/edition.ts`, while the document does not exist). Adapters reach per-event data only through `eventCollection(db, eventId, name)` and get the id from `ActiveEventResolver` (cached 60 s; a failed read throws instead of guessing). Accounts, roles and admins are global; an attendee registers again in each edition (alias unique per edition).
- `config/app`: `activeEventId`. Server-only.
- `team/{uid}` (global): `email`, `displayName`, `role` (staff|admin), `updatedAt`. Server-only; the list shown in the admin Equipo screen. The role *claim* is what grants access; this record lets the admin list people and enforces the last-admin rule in a transaction.
- `audit/{id}` (global, append-only): `action`, `actorUid`, `targetUid`, `details`, `at`. Server-only.
- `events/{eventId}/participants/{uid}` (was `users/{uid}`): `alias`, `aliasLower`, `role` (attendee|staff|admin), `squad` (angular|cloud|firebase|null), `xp` (0), `credits` (0), `createdAt`, `schemaVersion`.
- `events/{eventId}/checkins/{uid}_{checkpointId}`: `uid`, `checkpointId`, `kind`, `at`. Server-written only; the deterministic id is the idempotency key. A cadet can read their own.
- `events/{eventId}/checkpoints/{id}`: `kind` (entrance|talk|catering), `active`. Server-only; managed from the admin in phase 2.
- `events/{eventId}/aliases/{aliasLower}`: `uid`. Reserved in the same transaction as the user document to guarantee unique aliases.
- Rank is never stored; it is derived from `xp` by `rankFor(xp, ladder)`. The ladder (`EDITION.ranks` in `shared/config/edition.ts`) is configuration: stable ids, XP thresholds, and levels by position, validated by `createRankLadder` (starts at 0, strictly rising). Gates refer to levels, not names. Spanish names live in `shared/copy` (`rankName`, with a "Nivel N" fallback). Phase 4 will load the ladder from `events/{eventId}/config/ranks` and let the admin edit it; the functions already take the ladder as a parameter.
- **Alias rules** (domain, `Alias` value object): 3 to 16 characters; letters of any language, digits, `_` and `-`; no spaces; NFC-normalized; uniqueness key is the lowercase form; a small reserved list (admin, staff, organizador, gdg, devfest...) prevents impersonating the organization.
- **Registration** is one Firestore transaction that creates the participant and `aliases/{aliasLower}` documents together, and is safe to retry: an existing uid resolves as already registered and only re-applies the idempotent role grant. The role grant never downgrades staff or admin.
- `schemaVersion` is stored on every user document to allow future migrations.
- **Field ownership in `participants/{uid}`:** the cadet feature owns `alias`, `aliasLower`, `role`, `xp`, `credits`, `createdAt` and `schemaVersion`; the squads feature owns only `squad`; the check-ins feature owns only `attendedAt` (stamped by the first entrance check-in). Collection names live in `shared/lib/firebase/collections.ts`.
- **Squad ids are stable slugs** (`angular`, `firebase`, `gemini`), not a closed list: the profile stores the slug, and a squad retired from the catalog keeps a valid profile. Names, taglines and the 16x16 logo of each squad are catalog data (`SquadCatalog` port; static list today, database-backed in phase 2).
- **Phase 3 collections** (all server-only, under `events/{eventId}`):
  - `quadrants/{id}`: `name`, `tagline`, `planet` (a built-in planet kind), `order`, `active`. Stable slug ids; deactivated, never deleted.
  - `venue/map` (one document): the venue plan as data: `width`, `height` and `areas[]` (`id`, `kind` auditorium|stand|entrance|catering|service, `label`, `quadrantId` for stands, `rect` in plan units). Validated by the domain (`validateVenueMap`: inside the plan, unique ids, stands point to an existing quadrant).
  - Until the edition saves its own quadrants and plan, the catalog serves the bundled defaults (`DEFAULT_QUADRANTS`, `DEFAULT_VENUE`: a fictional venue with the auditorium in the middle and the stands around it). The admin edits and saves them in module 4.
  - Planned for module 2: `missions/{id}` (type, quadrant, xp, type-specific config, `order`, `active`, `minigame` null until phase 5), `missionCompletions/{uid}_{missionId}` (attempts used, outcome, XP earned) and the XP ledger `xpLedger/{uid}_{sourceId}` (`uid`, `source`, `amount`, `at`); granting XP creates the ledger entry and increments `participants/{uid}.xp` in one transaction, so a retry never grants twice. Source ids: `mission:{missionId}` and, in phase 5, `minigame:{missionId}` for the bonus.
  - Quiz: two attempts; a right first answer earns the full XP, a right second answer half (rounded down), two wrong answers close the mission without XP. Keyword: unlimited attempts behind the attempt limiter.
- **Squad assignment** is one transaction that reads the document and sets `squad` only when none is set, so two simultaneous taps cannot assign two squads and a repeat call returns the existing squad. The draw uses `crypto.randomInt` (uniform, injected into the domain as a picker).

**Security Rules** (`firestore.rules`, tested with the emulator)
- `events/{eventId}/participants/{uid}`: a signed-in user may read their own document; no client writes.
- `events/{eventId}/checkins/*`: read only your own (`uid` matches); no client writes.
- `events/{eventId}/checkpoints/*`, `events/{eventId}/aliases/*` and `config/*`: no client access.
- `events/{eventId}/squads/*`, `quadrants/*`, `venue/*`, and in phase 3 `missions/*`, `missionCompletions/*`, `xpLedger/*`: no client access (read on the server through cached catalogs).
- Default deny for everything else. Later phases open reads deliberately (leaderboard, checkpoints).

**Realtime:** not in phase 1. In phase 2, `onSnapshot` is wrapped in an Observer port and always returns its unsubscribe function.

**Server code:** server actions and route handlers in phase 1. Cloud Functions are reserved for scheduled or event-triggered work in later phases (for example leaderboard aggregation).

**Environment**
- `NEXT_PUBLIC_FIREBASE_*`: public web config only.
- Admin credentials (service account) and any third-party keys: server-only, never in public variables or client bundles.

**PWA:** manifest and service worker (Serwist or the equivalent compatible with the Next.js version in use; confirm at setup), update-prompt component, static assets cached. Authenticated data is not cached offline in phase 1.

**Theming:** dark-only theme through CSS variables in `:root`, mapped to Tailwind semantic tokens; applied server-side to avoid flash. Coordinated with `shadcn-ui-designer`.

## Provider portability rule
Goal: moving from Firebase to another backend (for example Supabase) rewrites only `data/` adapters, `shared/lib/firebase`, composition and the security rules; domain, use cases, hooks and UI stay.
- Every ports file (`domain/ports.ts`, repository interfaces) uses only domain types: no Firebase types, no `Timestamp`, no `DocumentReference`, no token or SDK concepts in names or signatures.
- Auth ports are neutral: sign-in returns an opaque `credential` or a `redirecting` state (`resumeSignIn()` finishes redirect flows); `SessionService` decides what the credential means.
- Modules 2 and 3 expose all data access as Repository ports (`AttendeeRepository`, `SquadRepository`) with mappers in `data/`; nothing outside `data/` and `shared/lib/firebase` imports `firebase` or `firebase-admin` (enforce with a lint rule `no-restricted-imports`).
- Not portable and rewritten on migration: Security Rules (to RLS policies), the `role` custom claim (to the new provider's metadata), transactions (alias reservation) and realtime adapters.

**Considered and rejected**
- Server-verified mini-games only: chosen against by the organizer (arcade reflex games, trusted results); the ticket and minimum time keep the bonus to one per mission.
- Mini-games as a mission type: they are a bonus on a completed mission (phase 3 decision).
- A map library (Leaflet, Mapbox): the venue is a small indoor plan, not geography; an own SVG from data is lighter, works offline and themes with the tokens.
- Admin-defined mission types: proofs must be validated by code on the server; types are a closed set of strategies.
- Strategy for squad assignment: the roadmap only asks for random assignment (one variant). Revisit if balanced assignment is requested.
- State machine and Observer: no stateful flows or realtime in phase 1; both arrive in phase 2.
- Decorator (cache): no repeated reads yet.
- Idempotency key: not needed in phase 1; planned for phase 2 check-ins.

## Principles and quality rules
- **Dependency rule:** `ui → domain ← data`; use cases depend on interfaces; wiring only in `app-shell/composition`.
- **SOLID:** small repository interfaces per aggregate (no generic "DataService"); extend by adding adapters, not by editing use cases per provider.
- **Naming:** all identifiers, files and comments in English; `PascalCase` components and entities, `camelCase` functions, `kebab-case` non-component files.
- **File size:** components under ~200 lines; split otherwise.
- **Typing:** TypeScript `strict`, no `any`; Firestore documents typed through mappers.
- **Error handling:** typed `Result` at the use-case boundary; error boundaries per route group (`error.tsx`); user-facing messages from `shared/copy`.
- **State:** local state first; context for auth only; server state through server components; URL for shareable UI state; avoid prop drilling beyond 3 levels.
- **No business logic in UI components; no provider SDK calls from presentation.**
- **Server-to-client props are plain data.** A page may pass a client component only serializable values and Server Actions; links go as base paths (`editBase: "/admin/escuadrones"`), never as functions. Page tests assert the exact plain `hrefs` (found 2026-10-09: two admin screens failed with a 500 that unit tests could not see).

## Security
- **Secrets:** Admin credentials and third-party keys only on the server; `NEXT_PUBLIC_*` holds public config only.
- **Input validation:** schema validation (Zod) at server actions and route handlers before reaching use cases.
- **Access control:** enforced in Security Rules and server guards, not only in the UI. Roles from custom claims set by trusted server code.
- **Economy integrity:** `xp`, `credits`, `role` and `squad` cannot be written by the client; the registration action initializes them to safe defaults.
- **Alias uniqueness:** reserved transactionally in `aliases/{aliasLower}`; registration is idempotent per `uid`.
- **Abuse:** all writes require authentication; registration is limited to one profile per `uid`. Rate limiting for repeated check-ins is designed in phase 2.
- **Session:** HTTP-only, secure, same-site session cookie.

## Performance and observability
- **Rendering:** server components for the first load; client components only for interaction; code-split by route group.
- **Caching:** cadet data is per-user and dynamic; invalidate with `revalidatePath` after mutations. Phase 6 leaderboard uses aggregated documents, not per-cadet listeners.
- **Budget (mobile):** keep the initial JS small; lazy-load motion-heavy and scanner code (phase 2); pixel art as optimized SVG or sprite assets at integer scales.
- **Error boundaries:** per route group and per dashboard widget.
- **Logging:** structured logs on server actions (action name, uid, outcome, never secrets).
- **Metric:** `analytics` port with events `attendee_registered`, `squad_assigned`; `checkin_completed` is added in phase 2.

## UI components
_Owned by shadcn-ui-designer. Decided 2026-10-03._

- **Strategy:** shadcn/ui + Adapter.
- **Libraries:** shadcn/ui (Radix primitives) with Tailwind CSS, `lucide-react` for icons, Framer Motion for motion (Design System). Exact versions are pinned at project setup.
- **Folders:**
  - `src/shared/ui/primitives/`: shadcn output, kept untouched.
  - `src/shared/ui/`: project adapters and own base components; the only import point for views (`Button`, `Card`, `ProgressBar`, `Skeleton`, `BottomNav`, `XpTag`, `RankChip`, pixel-art components...).
  - `src/features/<module>/ui/`: feature compositions built only from `shared/ui` (for example `PlayerCard`, `DashboardView`).
- **Adapter rule:** views and feature components never import from `primitives/` or from Radix directly. A new variant extends the existing adapter; no sibling components for the same purpose. Theme-specific components (pixel art, `XpTag`, `RankChip`) are written by hand inside `shared/ui`.
- **Icons:** `lucide-react` wrapped by one `Icon` adapter in `shared/ui` (stroke 1.8, round caps, `currentColor`), exposing the Design System icon names. Pixel art is never used as a UI icon.
- **Styling:** Tailwind with semantic tokens (`background`, `foreground`, `primary`, `accent`, `muted`, `border`, `destructive`) mapped from the Design System CSS variables. No hardcoded colors in components.
- **Theme approach:** `next-themes` with `defaultTheme="dark"`, `enableSystem={false}` and `attribute="class"` (no flash of the wrong theme). Only the dark palette exists in the Design System, so no light palette is generated and no toggle is shown; a second theme requires a new Design System palette first.
- **Motion:** Framer Motion through the shared motion tokens and reduced-motion hook (`shared/motion`).
- **Surfaces:** `(attendee)` mobile-first layout with bottom navigation (side rail from 760px); `(staff)` and `(admin)` layouts are created in phase 2.
